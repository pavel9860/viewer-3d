## Corpus result (one combined run, 2026-11-22 after DXF)
`cadcli corpus samples samples/catia`:
- 1,779 files decode cleanly; 241 decode with reported losses; 0 fail; 0 internal errors.
- DXF: 131 clean, 108 with losses (text, ACIS, images…), 0 failures, the R1.4 file rejected as expected. All 224 sample DXFs are clean under ASan + UBSan.
- 0 failures (2026-11-23). The 14 CAA SDK CATProducts that failed now decode: R11 store variants (segment tables numbered 1..n and listed in any order; a separate "CATIA_V5 CB0001" catalog block named in header bytes 16..23; empty streams with 0 segments), application product classes, and the object containers with inline names (SPEC/OSMN/OSMB). Their linked CAA parts are B-rep only (reported). Not covered by ground truth: no CATIA export of these products exists online (all copies are byte-identical; a CAA sample comment describing one assembly contradicts its own file on two placements). `tests/test_catproduct.cpp` checks the decoded trees as a regression.
- Wider CAA corpus (`samples/caa/caadoc/`: 862 CATPart/CATProduct files of the CAA documentation archive, 2026-11-23): CATProducts 76 clean, 162 with reported losses, 14 failing (at first: 33 / 40 / 179). Losses: parts stored only as exact B-rep (55 products), application data in extension containers (piping, electrical, manikins; reported by container), documents missing from the archive. Failing, each form seen in one writer family only (reported, not fitted): flattening/animation samples whose chunks mix closing fe and prefix names (5), electrical harness relation values <name> fb|fd <link> (3), architect_level header without fe before an ambiguous byte (1, +2 linking it), CAAKniClash with fewer relation blocks than objects (1); two CAASch files whose Data stream holds stale bytes between sections and whose index then disagrees (damaged); a text file named .CATPart (correctly rejected). Grammar facts established on this corpus are documented in `catia/spec.hpp`, `catia/osm.cpp`, `catia/data.hpp`, `catia/document.hpp`.
- Object-stream grammar, generalised over the whole corpus (~2,200 files, ~1.1 M relation blocks) instead of per file: relation headers depend on the OSM version (from 35: a reference-kind byte 00/01 when head bit 2 is set, a class name for forms 1 and 5; before 35: a leading token when head bit 1 is set, optional inline class definition, closing fe), the relation body is located by its framing (the one 7c 0a record reaching the block end), object headers are <class> <handle> <stamp> <stamp> (GUID | 80 + 5 bytes) <kind> [compact for odd kinds] in OSM and SPEC alike, and the SPEC field set per version is a table (`spec.cpp`, struct Layout). Unit tests per form: `tests/test_catia_grammar.cpp`.
- CATPart/CATProduct warnings: the B-rep-only parts (exact geometry, no stored tessellation) and their assemblies, plus Human Builder manikins.

## Test infrastructure
- `cadcore_tests`: 31 cases, 10,453 assertions (DXF: generated parts in ASCII, binary R13+ and binary R12, plus analytic cases for arcs, bulges, OCS, ellipses, splines, inserts and arrays, colour inheritance, hatches, thickness, polyface, REPEAT, rejection of broken streams); exact geometry for every format variant; truncation and byte-flip fuzzing; buffer alignment; Draco against ground-truth sources. Clean under ASan + UBSan.
- `cadcore_perf` (separate binary, `ctest -R perf`): every writer variant on generated models whose input size doubles three times (long strips, one face per quad, 1k-8k instances). Each timing is the minimum of 5-25 decodes; the fitted growth exponent must be <= 1.3 (all measure 0.9-1.16), and throughput at the largest size must stay above a floor of 1/4 of the 2026-11-22 measurement (skipped under sanitizers). One re-measurement is allowed per series. Stable in repeated runs and under a concurrent 5-job build. It found and drove the fix of a quadratic glTF path (primitives sharing a vertex buffer: 9.6 s -> 0.12 s).
- Speed target (2026-11-22): `cadcli benchsuite DIR... --check BASE.tsv --speedup 10` fails every format whose total decode time over its baseline files is not 10x below the baseline (the readers as of 2026-11-22; DXF, CGR, 3DXML entries recorded the same day). **Not met yet** (run of 2026-11-22, about ±10% run-to-run): CATProduct 6.4x, PLY 3.9x, 3MF 3.5x, CATPart 2.8x, OFF 2.6x, STL 2.5x, GLB 1.8x, glTF 1.7x, 3DXML 1.2x, DXF 1.2x; OBJ, Draco, CGR about 1x. DEFLATE: zip entries of 1 MB or more decode in parallel by speculative decoding (`codec::inflate_parallel`: block starts found by search, parts decoded with an unknown 32 KB window, accepted only when each part ends exactly where the next begins, otherwise sequential); the largest 3MF went from 454 ms (baseline) to about 75 ms, and its stream from 57 to about 30 ms; equality with sequential decoding (also on corrupted streams) is a unit test. Remaining limits: CATPart face-list parsing (about 9 ns per triangle), DXF block expansion (sequential), many small files where fixed per-file costs dominate. OBJ was tried as a two-phase parallel parse and reverted: +7% with 6 threads, -58% with one (its cost is in index resolution, not parsing). With 1 thread no format is slower than its baseline. Decoders use up to 6 threads (`DecodeOptions::threads`, `CADCORE_THREADS` in cadcli; a persistent pool in `src/core/parallel.cpp`); 1-thread and 6-thread output is identical on all STL, CATPart and CATProduct files, and ThreadSanitizer reports no races.
- `cadcli benchsuite DIR... --write/--check BASE.tsv`: min-of-5 decode time of every corpus file against a per-machine baseline (`cadcore/tests/fixtures/bench_baseline.tsv`, recorded on the development machine); a file fails when > 1.5x + 2 ms slower. Repeat runs report 0 false slowdowns over 1,768 files.
- `cadcli compare A B TOL`: order-independent triangle/point matching between two files (used for the Draco ground-truth checks).
- No third-party code is compiled or linked; `cadcore/third_party` has been removed.
- CATProduct: `tests/test_catproduct.cpp` compares the decoded tree with `tests/fixtures/*.occurrences.tsv`, written from STEP exports by `cadcore/tools/step_assembly_gt.py`. `cadcli ply FILE OUT` writes the assembled triangles for visual review.
- `cadcli corpus samples …`: strict. A warning (lost content) counts as a failure unless `expectations.tsv` lists the file, with a reason verified by reading it.
- `cadcli gen DIR`: writes all generated parts (`samples/generated/`).
- `cadcli dxfcheck FILE...` (2026-11-22): the decoded drawing's world box against the extents stored in the file ($EXTMIN/$EXTMAX). Stored extents are only ground truth when the writer computed them: a file whose own LINE/POINT/CIRCLE/ARC geometry (exact boxes, computed from the groups alone) lies outside them is reported UNRELIABLE; z is compared only when stored (R11+); RAY/XLINE are excluded; tolerance 5e-4 of the drawing size (AutoCAD's curve extents are approximate). Corpus: 38 MATCH, 89 INSIDE, 5 OUTSIDE, 3 UNRELIABLE. All 5 OUTSIDE were reviewed: one real gap (XCLIP clipping boundaries, now reported as a loss), four with placeholder extents (libredwg test files: (-1,-1)-(14,14) or (15,15); ezdxf: +-100). INSIDE files without warnings reviewed so far: user files Hole1/Hole2/part-cbe2 (the exporter writes z = 2 and leaves arcs out of the extents), PolylineSplineFit, hatches_1 (extents not those of the content). Open: Constraints.dxf (extents include dimensional-constraint annotations not drawn), block.dxf, hatch_issues.dxf, custom_blocks.dxf, cc_dxflib.dxf, small_r14.dxf.
- `cadcli svg FILE OUT.svg [PX]`: top view of triangles, polylines and points, for visual review of 2D formats.
- Fixed under UBSan (2026-11-22): the CATIA tessellation reader passed a null pointer to `memcpy` for an empty point list (CGR test).
